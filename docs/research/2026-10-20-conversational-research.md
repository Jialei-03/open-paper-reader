# 研究从对话开始：阶段、记录、算力与实验追踪（2026-10-20）

## 为什么改

原来的研究入口是一张表单：先填问题、背景、轮数，然后 Agent 自己跑到底。实际用下来有两个问题：

- 研究计划不是填表就能填出来的。目标、基线、什么算成功、什么时候止损，都要来回商量才能定。
- 人没有位置。整个过程只在开头给个题目，中间要拍板的事没有固定入口。

现状调研（[landscape](2026-10-20-landscape.md)）的结论与此一致：关键节点上的判断目前该由人来做，但人介入的次数不是越多越好。

## 现在的流程

研究分四个阶段，各阶段之间的切换都记成 `stage_changed` 事件：

1. **定题（scoping）**
   - 研究者用一句话开头，和导师对话。
   - 导师查文献、追问基线和限制，用 `propose_plan` 把计划写成对话里的一张卡片。每改一次就出一个新版本。
   - 计划卡片包括：问题、指标、基线、目标，以及若干假设（每个都带止损条件），还有数据集、算力和预算。
   - 研究者点“开始实验”后，计划才写进研究地图，数据集才开始下载。这个阶段不跑实验，也不计入预算轮次。
2. **实验（experiments）**
   - 执行者和导师轮流推进，和原来一样。
   - 研究者随时可以插话。说了话之后，下一轮由导师先在对话里回应，再安排后续。
3. **结论（conclusion）**
   - 导师认为证据足够时，会提出一个结论，但结论不会立刻生效，要等研究者处理。
   - 研究者接受，项目结束；研究者要求补做，项目回到实验阶段，研究者的意见写进后续的简报。
4. **复盘（retrospective）**：提炼者提出手册规则。复盘结束后项目进入 done。

评测运行（`budget.auto_decide`）没有人可问，所以跳过定题阶段，结论也按提出的直接生效。

## 结构化记录

| 记录   | 存在哪里                                                             | 内容                                                                        |
| ------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 阶段   | `research_projects.stage`，以及 `stage_changed` 事件                 | 当前阶段和切换历史                                                          |
| 计划   | `research_projects.plan`，以及每个版本对应的 `plan_proposed` 事件    | 研究者批准的那一版及批准时间                                                |
| 对话   | `message` 事件                                                       | 研究者、导师和系统说的话                                                    |
| 数据集 | `research_datasets` 表                                               | 来源（系统下载或研究者上传）、每个文件的 md5 和 sha256、大小、状态          |
| 算力   | `research_projects.compute_id`、`research_jobs.compute_id`           | 每个作业在哪台机器上跑                                                      |
| 环境   | `research_projects.environment[compute_id]`                          | 每台算力首次运行时自动检测：Python、操作系统、CPU 和内存、GPU、主要包的版本 |
| 运行   | `research_jobs` 的 `config`、`metrics`、`points`、`tracker_url` 字段 | 作业通过 `ora` 模块报告的超参、最终指标和曲线点数                           |
| 结论   | `research_projects.conclusion`                                       | 结论内容、研究者是否接受，以及研究者的意见                                  |

### 实验通过 `ora` 报告指标

实验脚本用 `import ora` 报告超参和指标：

```python
import ora
ora.config({"lr": 1e-3, "epochs": 5, "seed": 0})
ora.log({"train_loss": loss, "val_acc": acc}, step=epoch)
ora.summary({"test_acc": final})
```

这个模块只依赖标准库，以只读方式挂在 `/opt/ora`。

- 每次调用都会在作业日志里打一行 `ORA_SUMMARY ...`。研究结论引用的就是这一行，所以证据规则不变。
- 文件写进一个只有这个作业能写的目录 `/ora-run`。智能体的文件工具看不到这个目录，所以它没法事后改动指标。

## 数据

- 实验容器没有网络。公开数据集由系统在本机下载，按发布方给的校验值核对后，以只读方式挂在 `/data/<名字>`。
- 目前可下载的有 MNIST 和 CIFAR-10。
- 研究者上传的文件也会记下 sha256。

## 算力

算力在“设置 → 研究：算力与实验追踪”里配置，配置文件存在 `<数据目录>/research/settings.json`。

- **本机 Docker（默认）**：容器没有网络，根文件系统只读，并且可以设置 CPU 和内存上限。如果在 Linux 机器上，填了 GPU 就会加上 `--gpus`。
- **SSH 机器**：
  - 主机用 `~/.ssh/config` 里的名字，或者 `user@host`，以非交互方式登录，系统不保存任何密码。
  - 每个作业运行前，用 rsync 把工作区和数据集传过去；作业结束后，把工作区和 `ora` 的报告传回来。
  - 作业在后台运行，有两种运行方式：直接运行（可以指定 `CUDA_VISIBLE_DEVICES`），或在远端用 Docker `--gpus` 运行。
  - 退出码写在日志旁边，系统据此区分“已结束”和“丢失”。

## 实验追踪

可以选 SwanLab 或 Weights & Biases，同步方式有“只记在本机”和“上传云端”两种。

- 每个作业结束后，系统在本机用一个子进程把它同步过去，子进程有超时限制。同步内容包括超参、所有曲线点、最终值，以及标签（阶段、算力、状态）。
- API 密钥只保存在本机的设置文件里，不会返回给浏览器，也不会进入实验容器。
- 后端依赖用可选的 extra 安装：`pip install '.[tracking]'`。
