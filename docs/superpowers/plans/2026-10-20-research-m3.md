# Open Research Agent M3：自我改进的研究手册与评测框架 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** 研究过程跨项目自我改进（不改模型权重）：每个项目结束后，一个独立的"提炼者"从项目记录中提炼判断规则，写进版本化的研究手册；后续项目的执行者和导师读这本手册。再配一个评测框架，在事先封存的任务上，用对照组证明"手册让研究过程变好了"。

**Why（来自调研）：**
- ExpeL、AutoGuide、Dynamic Cheatsheet、Agent Workflow Memory 证明了"从经验提炼规则、测试时注入"有效。
- Xiong et al.（2505.16067）表明：只加不删的记忆会让错误传播，有选择地增删效果更好。
- DGM 和 AIDE²（2609.26457）表明，自我改进的循环会钻自己指标的空子，因此必须在封存的任务上评测，用改进循环从未见过的打分方式。
- 我们的差异：提炼的是**研究判断**（何时止损、何时转向、如何避免偏离），来源是导师的判断和止损记录，而不是代码或工具用法。

## Global Constraints

- 手册存在数据目录 `research/playbook.json`，版本化：每次修改递增版本，并记录 `history`（谁、哪个项目、什么操作）。规则上限 40 条。
- 每条规则：`{id, when, do, why, sources: [project_id], helpful, harmful, status: pending|active|retired, created_at}`。
- 准入：同一规则（或经 MERGE 合并的规则）被至少 2 个项目支持，或经人工批准，才从 pending 变为 active。只有 active 规则会注入。
- 剔除：`harmful >= helpful + 2` 时自动退役（retired），并记录事件。
- 评测：任务集分为"学习集"和"封存集"，封存集永远不参与提炼。
- 其余同 M1、M2 的全局约束。

## Review Focus

1. 提炼者输出的规则过长或过泛（比如"要认真做研究"）：拒绝长度超限或无 `when` 条件的规则。
2. 手册文件损坏或丢失：退回到空手册，不阻塞研究。
3. 规则注入撑爆上下文：注入的 active 规则最多 12 条，按 `helpful - harmful` 排序。
4. 同一项目被提炼两次：幂等，第二次跳过。
5. 评测脚本中途失败：已完成的任务结果保留，可以续跑。

### Task 1: 研究手册存储与注入

**Files:** Create `backend/research_playbook.py`；Modify `backend/research_brief.py`（执行者和导师的 brief 都加"研究手册"一节）；Test `backend/tests/test_research_playbook.py`

**Interfaces:**
- `load(settings) -> dict`：文件不存在或损坏时，返回 `{"version": 0, "rules": [], "history": []}`。
- `save(settings, book)`：先写临时文件，再原子替换。
- `apply_ops(book, ops, project_id, actor) -> dict`：处理以下操作，并返回 `{"added", "edited", "merged", "deleted", "rejected"}`。
  - ADD `{when, do, why}`：新规则 status=pending，sources=[project_id]；
  - EDIT `{id, when?, do?, why?}`；
  - MERGE `{ids, when, do, why}`：合并多条为一条，sources 取并集，任一来源为 active 则为 active，否则按来源数准入；
  - DELETE `{id}`：status 置为 retired；
  - VOTE `{id, helpful: bool}`：对应计数加一；
  - 校验：`when` 和 `do` 必填，`when` 不超过 200 字，`do` 不超过 300 字，`why` 不超过 300 字；
  - 准入：sources 不少于 2 条时，status 由 pending 变为 active；
  - 剔除：harmful ≥ helpful + 2 时 status 置为 retired；
  - 上限：超过 40 条时，按 `helpful - harmful` 退役最低的 pending 规则。
- `for_brief(book, limit=12) -> str`：按"在 X 情况下，做 Y（因为 Z）"格式列出 active 规则；没有规则时返回空串。

### Task 4: 评测框架

**Files:** Create `scripts/research_eval/run.py`、`scripts/research_eval/tasks/*/task.json`（question、background、data 生成脚本、`score.py`、split: learn|heldout）、`scripts/research_eval/report.py`

**Interfaces:**
- `run.py --tasks <split> --condition <playbook|no-playbook|no-advisor|frozen:<version>> --seeds 3 --max-sprints N --out results/<run>.jsonl`：通过本机版 API 创建项目，放入数据，开启 auto_decide，等项目结束；然后调用 `score.py`（读取最终地图和作业日志，给出 0–1 分及理由），再写一行结果：task、condition、seed、score、metrics、tokens、轮数。支持续跑：已有结果的条目跳过。
- `report.py results/*.jsonl`：按条件汇总平均分、偏离率、回头延迟、tokens，输出 Markdown 表。
